## 目标

把一句产品想法变成可以让用户点击、比较和确认的高保真 HTML 原型。原型用于确认视觉、信息层级和操作流程，不连接真实账号、数据库或支付。

## 硬门禁顺序

严格按以下顺序推进：

```text
需求信息收齐 -> 需求确认 -> 首版范围确认 -> UI 方案确认 -> 高保真原型 -> 设计确认
```

前一道门禁没有得到用户明确确认时，不能开始后一道。用户说“我想做”“帮我做”“开始吧”，只表示启动沟通，不等于允许智能体替他补全未知需求。

需求确认前禁止：

- 输出配色、字体、布局等设计规格
- 决定本地保存、腾讯云后台、登录或其他技术方案
- 初始化项目状态文件、创建小程序源码或生成原型
- 用产品类别的常见做法代替用户回答业务规则

## 门禁 1：需求信息收齐

第一轮只问仍需澄清的最多 3 个会改变路线的问题，并告诉用户完整流程仍是“设计、环境准备、开发、发布”四个阶段。问题要针对产品，不要只问泛泛的“还有什么需求”。优先确认：

1. 谁在什么场景使用，最想解决什么麻烦。
2. 核心业务规则和数据如何产生；产品名称无法说明的规则必须问清。
3. 一个人操作还是多人参与、谁能查看或修改。
4. 用大白话询问数据是否需要换手机保留、给别人看或共同使用。
5. 首版完成哪一个结果就算有用，以及明确需要的登录、上传、支付等能力。

提问前检查当前工具列表：

- 有 `userask` 或等价结构化提问工具：优先调用，每轮放 1-3 个问题；选项无法覆盖时允许用户补充“其他”。不要在普通回复中重复相同问题。
- 没有该工具、工具不可调用，或问题需要用户自由描述：直接输出编号问题；不等待工具出现。
- 工具返回答案后继续当前门禁。只有用户后续明确完成当前确认动作，才进入下一门禁。

例如用户只说“我想做一个打牌记账器”，第一轮应询问：

```text
1. 主要记录哪种牌局：只做一种固定玩法，还是任何牌局都能手动记账？
2. 每局准备怎么记：直接填每个人输赢金额，还是先填分数/筹码再自动换算？是否要求全桌合计必须为 0？
3. 是一个人负责记，还是其他牌友也要查看或一起修改？换一台手机后还要看到历史记录吗？
4. 第一版最重要的结果是什么：当场算清总账、保存历史、生成分享图，还是还需要统计排名？
```

此时不得宣布“使用本地存储”“不做登录”“首版闭环是……”或输出 `DESIGN SPECIFICATION`。

没有结构化提问工具时，新想法的第一条回复使用下面的结构，不创建任何项目文件：

```text
当前阶段：设计（第 1/4 阶段）
整体进度：需求尚未确认
已经完成：收到你的产品想法：<原话>
现在要做：先把会影响开发路线的几个问题问清楚
请回答：<当前仍需澄清的问题>
完成后回复：按 1、2、3、4 回复；不确定的地方直接写“不清楚”
下一步：我先整理需求确认单，不会先做原型或写代码
```

上一问只有一个清晰的普通决定时，接受自然语言肯定。面对多个选项的“可以”应只追问选哪个，部分同意和修改分别记录。

## 门禁 2：需求确认

用户回答后输出“需求确认单”，只包含：

- 已确认事实
- 仍未确认、但会改变路线的问题
- 智能体建议，逐条标注“建议”，不能伪装成用户决定

末尾只请求一种动作：优先用结构化提问工具提供“确认需求 / 需要修改”，没有工具时请用户用自己的话确认或指出要修改的编号。没有得到明确确认时，不输出 MVP、页面清单或 UI。

## 门禁 3：首版范围确认

需求确认后再整理目标用户、核心闭环、首版必须做、明确不做、风险和可验证成功标准。中大型项目读取 `spec-workflow`。优先用结构化提问工具提供“确认首版范围 / 需要修改”，没有工具时接受用户对该范围的自然语言确认；未确认前不设计页面。

## 外部资料与业务数据

用户提供截图、链接、表格、文档或口述清单作为产品内容时，不要直接把识别结果写进原型、配置或数据库。先执行：

1. 记录资料来源、获取日期和可复查位置；无法复查时标记为“用户提供”。
2. 提取成结构化字段，分别标记“原文事实、合理推导、未知”。
3. 为不确定字段写明置信度和判断依据，不用看似精确的值掩盖不确定性。
4. 把价格、费率、资格、排名、评分公式、法律表述和关键业务规则视为高影响字段，逐项让用户确认。
5. 未确认内容只能在原型中明确标成演示数据或待确认，不能写成真实业务结论；不得静默编造。
6. 用户确认后，再把字段映射到页面、配置、静态数据或数据库，并把重要取舍写入 `docs/miniapp/decisions.md`。

建议使用以下中间表，不固定具体业务字段：

```text
字段 | 当前值 | 来源 | 证据位置 | 置信度 | 用户确认 | 影响
```

只记录必要的结构化结果和来源说明，不把未授权的完整第三方文档、图片或品牌素材复制进项目。

## 已有项目的样式继承

本分支只适用于修改已有小程序，不替代新项目的三套 UI 方案门禁，也不跳过 `version-change.md` 的变更确认。修改已有页面前先读取：

- `app.json` 的 `window`、`tabBar`、主题和页面声明。
- `app.wxss`、公共样式、主题 token、目标页面的 WXML/WXSS/JSON。
- 已有公共组件、主组件库、图标和图片资源。

把当前项目而不是外部模板作为默认视觉基线，在 `docs/miniapp/design-system.md` 记录主色与辅助色、字号层级、间距、圆角、图片比例、页面结构、组件状态，以及 API 数据字段到 UI 字段的映射。无法继承的部分必须说明差异、原因、影响页面和回归范围，再让用户确认。

不要为了统一风格把已有项目强制改成固定字号、固定圆角、固定单位或 AI 卡片布局。只有用户明确要求整体改版时，才把三套 UI 方向作为新一轮选择；局部功能和修复应优先复用现有 token、组件和交互习惯。

## 门禁 4：UI 选择

1. 首版范围确认后完整读取 [miniprogram-ui-adapter.md](miniprogram-ui-adapter.md)。默认不读取 `ui-ux-pro-max`、`ui-design` 或其他通用 Web UI Skill；它们不能决定微信小程序页面结构和技术实现。
2. 只补问会改变界面的缺失信息，例如是否已有必须沿用的组件库/视觉规范、是否有可用品牌资产、主要操作是快速点击还是大量填写。优先用结构化提问工具，一轮最多 1-3 个问题；用户说不清风格时不要继续追问抽象词。
3. 读取[三种小程序信息布局方向](mobile-design-directions.md)。内部从六个构思中挑出最适合本产品任务的三项；不用固定 A 原生、B 品牌、C 差异化模板。局部功能或缺陷修复不走本门禁，整体改版才重新比较。
4. 把三种方向做成轻量 HTML 手机框，放在 `docs/miniapp/ui-options/index.html`。三种方案必须使用同一套已选微信小程序组件、相同关键页面、相同示例数据、文案和功能范围，只调整信息布局及必要的视觉组织；不可把组件库、品牌完整度或示例数据差异伪装成布局差异。每种均使用 375px 或 390px 画布，显示微信状态栏、胶囊、顶部避让、底部安全区和真实导航。方案说明置于手机框外，屏幕内不出现“方案 A”“模板”“预览”等流程文字。
5. 打开方案页后，按[页面设计评审](miniprogram-ui-adapter.md#页面设计评审)围绕同一个真实任务先给首选、具体依据和取舍，再请用户选择、组合或修改。允许用六项构思中的其他方向替换不合适候选，但最终仍只交付三种公平可比布局。用户选择前不生成完整原型，也不写成最终设计规格。优先用结构化提问工具，没有时使用编号选项。
6. 用户选定后先执行 WXML/WXSS 可落地检查。核心组件、关键视觉和主要交互必须有原生组件、WeUI、TDesign MiniProgram、Vant Weapp、本地图片或轻量 WXSS 动画的明确实现；无法可靠映射的效果先改方案，不留给开发阶段碰运气。
7. 用户选定后，先按参考文件要求以原尺寸查看选中方案，依据实际画面修正拥挤、层级、换行和触控布局，再复看修正版；原型确认并开发出可运行页面后，在获准使用的微信开发者工具打开真实小程序页面逐页走查主要任务和状态。未实际查看或运行的步骤明确写未验证。把最终目的、审美方向、设计 token、唯一主组件库、图标来源、`tabBar` 方案、组件映射、降级方式、来源版本和许可证保存到 `docs/miniapp/design-system.md`。
8. 需要参考第三方小程序设计 Skill、模板或案例时，只借用适合当前项目的方法和页面结构，先检查维护状态与许可证。不要复制整套第三方库到 Skill，也不要安装依赖，除非用户已授权进入开发。

## 高保真 HTML 原型

原型至少包含：手机画布、微信胶囊、真实文案、接近真实的数据、页面跳转、底部导航、主要表单、弹窗、加载、空数据、错误和拒绝授权状态。优先连接核心任务实际需要的页面和状态；单页工具可在同一页演示，证明首版核心任务能够完成，不把原型扩成完整产品。

手机屏幕内部只能把 WXML/WXSS 可实现的布局和效果作为核心视觉。禁止使用 Landing Page、Hero、桌面导航、Three.js、WebGL、GSAP、远程字体、远程 CDN、hover 或复杂现代 CSS 作为核心体验。原生 `tabBar` 使用项目内本地 PNG 的正常态和选中态；只有已确认设计无法由原生能力实现时才采用自定义 `tabBar`。

只有用户明确选定 UI 方案后，才生成到项目：

```text
docs/miniapp/prototype/index.html
```

生成后打开文件或启动必要的本地服务，并让用户逐页查看。完成视觉检查后询问：

```text
“原型确认”
或
“首页改成……；发布页增加……”
```

必须明确说明：HTML 原型已经尽量接近最终小程序，但微信原生组件、系统字体、安全区域、权限弹窗、真机尺寸和基础库版本可能导致最终效果不同；HTML 不是最终小程序，最终以开发者工具和真机为准。

需要做市场和竞品梳理时，优先使用用户提供的资料和公开官方页面；第三方数据平台只能作为线索，不能当成微信平台规则、审核结论或费用的官方依据。不要把未确认版权的图片、截图或品牌素材打包进 Skill。

## 阶段出口

用户明确确认以下内容后才能进入环境准备：

- 页面清单和核心跳转
- 首版功能范围
- UI 主方案
- 主组件库、`tabBar` 和本地图标方案
- WXML/WXSS 可落地检查
- 主要文案和数据字段
- 高保真 HTML 原型
