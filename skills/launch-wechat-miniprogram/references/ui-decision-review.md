# 画首页和列表时，怎样决定放什么

适用于发现页、预约、订单、管理台及其他需要扫读、比较或采取行动的页面。只做倒计时、核销等单一任务时，优先让用户看见结果和下一步，可以直接省去推荐、筛选和封面。

## 动笔前先试着替用户选一次

1. 写一个能选出结果的问题。例如「我现在走过去，哪家还开着，人均在预算内？」放两条真实结构的演示数据，故意让较近的一家已打烊。若看完首页只能点进去碰运气，就能找出漏了哪个字段。
2. 把两条内容摆在一起。决定两者谁合适的共同信息放同一个位置；只对某个品类有用的信息跟随品类。为每个标签问一句「去掉它，会影响哪种选择？」删掉重复标题、含义空泛、缺少数据来源的标签。评分、折扣或销量需要对应事实；原型注明演示数据。
3. 决定怎样排才好看。为一个页面指定第一眼的焦点；用共同左边线、字重、基线和留白表达层次。图片裁切要保住辨认主体，文字叠图要用亮、暗两种样图试读。让类别图标、标题、推荐图各自承担明确作用。将品牌标题和插图缩小一档做对照，用普通字体、长标题和缺图内容再看一遍，检查首屏能否露出有用结果。
4. 画主状态和一个会改变决定的状态，一起交给用户确认。例如满额、无定位、报名失败或订单待同步。业务数据缺失时保留可以使用的路径。计划中的功能、运营没有维护的数据以及测试开关不要进入正式展示图。

## 按页面选择字段

| 用户此刻要办的事 | 我会优先放什么 | 我会怎样检查 |
| --- | --- | --- |
| 在附近选一家店或一个展 | 标题旁放收藏，单位一致的距离与定位图标放每行相同的侧边位置。本例选右下角，左边留给门店营业状态、人均或展览票价、展期。选少量能区分候选的标签。 | 让人分别找「近且仍营业」与「免费且免预约」。关掉定位，改按所选区域浏览；没有坐标时隐藏米数。直线距离与步行路线、步行用时分别标明依据。点收藏时不应误入详情。 |
| 看预约还有哪一场可选 | 给同类场次固定的日期、地点、余位位置；满额用文字说明。详情和确认页复述用户刚选定的时间。 | 放两个同名活动或两个相邻时段，含一个满额项，检查从详情返回后原选择与列表位置；人数失效时保留其余输入。 |
| 工作人员处理订单 | 优先待办状态、处理期限与下一步；从某人详情带入的筛选应可见、可清除。金额、状态和动作分别对齐。 | 同一视口检查加载中、加载失败、筛选无结果。手动重试沿用条件。只在真实状态允许时提供处理动作。 |
| 提交内容、记账或整理计划 | 长输入明确能否恢复；区分已存本机、待同步与服务端已接收。替换已有内容时预告影响对象和数量。 | 写半条、退出再进、切账号、断网；执行会覆盖现有内容的动作再取消，检查原内容。 |
| 阅读、比较资源或开始单次任务 | 比较页固定指标名称、单位、时间与口径；示例旁提供复制。一次性工具把开始、暂停或结果放首位，低频设置后置。 | 切项是否仍能对照同一维度，复制到其他输入框是否可用；第一次打开单一工具能否直接开始。 |

## 从项目经验和外部研究学习

先找过去做过相同任务的页面、失败记录或两张实屏。读清是哪类人、在哪一步受阻、原方案为什么改、证据来自源码还是实际操作。跨项目只带走可解释的做法；客户数据、品牌图和专有代码留在原项目。找不到旧例时，到公开社区找线索，再看原创研究、组件示例和官方规范。记录「来源 → 当时任务 → 当前采用或舍弃的理由 → 验收动作」。题材相同但用户目标不同，允许得出不同排法。

- Baymard 的商品列表测试发现，缺少决定性属性会让用户反复进详情。有些属性能跨品类比较，另一些取决于品类。上面的门店与展览布局是对研究的迁移，距离的具体落点是本设计的选择。[原始研究](https://baymard.com/research-articles/product-listing-information)
- NN/g 的研究和设计说明给出了用标题引导扫读、利用尺寸、对比和分组安排注意力的方法。在手机原图上分别看第一眼的焦点和用户实际要点的入口，再决定是否降低图片或标题的权重。[扫读研究](https://www.nngroup.com/articles/layer-cake-pattern-scanning/) · [视觉层级](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/)
- W3C 对状态传达的解释可用于检查绿点、选中态和错误。组合文字、形状与颜色，再检查浅色标签的可读性。腾讯 TDesign 微信小程序的 Cell、Tag、Empty 可作为实现候选；用真实字段长短试组合后选用。[W3C 颜色使用](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) · [腾讯小程序组件示例](https://static.tdesign.tencent.com/miniprogram/)

## 从真实问题学来的界面细节

2026-11-22 核对了下面的作者说明、研究与源码。每项的「试一下」是给当前小程序的验收动作。先选与业务有关的场景，再决定是否需要组件。

| 什么时候用 | 借来的经验与小程序里的取舍 | 试一下 |
| --- | --- | --- |
| 店铺标签和筛选同时出现 | GOV.UK 把 Tag 用于展示状态，并记录了它被误认成按钮的问题。附近页可让「露台座位」用轻底色作说明；同屏可点的「步行可达」有触控区、选中标记和取消反馈。如果标签实际支持点击筛选，就按筛选控件设计。[Tag 设计与研究记录](https://design-system.service.gov.uk/components/tag/) | 只看灰阶图能否说出哪些可点；实际点选和取消后能否解释结果为何变化。 |
| 多条件藏在菜单里 | GOV.UK 的项目讨论提到清除入口太远、已选项不可见；Baymard 观察到在结果区逐项移除的价值。收起菜单后展示有辨识度的已选条件。若外层已有全部可见的快捷筛选，直接标选中即可，避免重复占行。腾讯为多选菜单补了收起后保持标题高亮的选项，可按项目版本评估。[项目讨论](https://github.com/alphagov/govuk-design-system/issues/5921) · [筛选研究](https://baymard.com/research-articles/how-to-design-applied-filters) · [腾讯实现](https://github.com/Tencent/tdesign-miniprogram/pull/4678) | 搜「版画」，加「今天开放」和区域条件直到零结果，只去掉「今天开放」。搜索词和区域应保留，结果刷新。 |
| 决定用卡片还是紧凑列表 | USWDS 区分成组内容、表格行和简单操作。移植到手机时看比较密度：周末路线由照片帮助识别，可以突出一组；多场次、订单或同款机器要快速纵向比较，让日期、余位或预计时间共享对齐线。只承担跳转的入口可收成一行。[卡片选用指南](https://designsystem.digital.gov/components/card/) | 给两种布局同一批长短名称，找「最早能洗完的一台」或「最近仍营业的一家」。看能否连续比较决定性属性，照片是否挤掉下一项。 |
| 表单报错把箭头挤歪 | 腾讯改过 FormItem 的布局，使箭头只和标签、输入控件对齐。预约页的「选择时段」也应把说明和错误独立排在下方；错误出现时箭头仍指向可点的选择行。这个案例适用于有附加说明的行。[腾讯修复及差异](https://github.com/Tencent/tdesign-miniprogram/pull/4693/files) | 从无错切到两行报错，再把系统字号调大。看箭头与输入行是否对齐，点击箭头是否仍打开正确选择器。 |
| 误触取消收藏 | Android 官方示例在收藏页移除后提供短时撤销。微信可用带「撤销」的页内反馈。在线保存失败时恢复先前图标并给重试；支持离线队列的产品则标明待同步。这两种失败策略是本 Skill 对实际写入方式的建议。[示例源码](https://github.com/android/nowinandroid/blob/main/feature/bookmarks/impl/src/main/kotlin/com/google/samples/apps/nowinandroid/feature/bookmarks/impl/BookmarksScreen.kt) | 在收藏列表移除再撤销，核对同一条恢复且无重复。模拟写入失败，再回到首页看两个入口的收藏状态是否一致。预约取消、支付退款需另核对业务可逆性。 |
| 翻过几页、进详情又回来 | 返回列表应能接着看刚才那条。对于分页和可变高度图片，可保留筛选、排序、已载页与条目 ID；记录条目在视口的位置。只记像素值在列表插入或图片高度变化时可能回到另一条。[返回位置研究](https://baymard.com/research-articles/return-same-place) | 滑到第二页末尾进详情，让上一行的图片迟到，再返回。核对同一条仍在合理位置；若已下架，保留上下文并给邻近结果。 |

## 素材替换、地图浏览和预约变化

下面是从其他产品借来的做法。先按项目所用渲染引擎、可用数据和用户任务判断是否采用。

| 画稿时容易漏掉什么 | 来源给了什么启发；小程序怎么取舍 | 交付前怎样验 |
| --- | --- | --- |
| 同一张图换比例后，店门或招牌被裁掉 | Shopify 的内容管理能给原图设焦点。门店横幅和列表缩略图共用素材时，明确最该保留的主体，并为标题留位置。少量精选内容可以直接导出两种构图，只有经常换图、入口多时才考虑加焦点配置。[Shopify 图片焦点](https://shopify.dev/docs/api/liquid/objects/focal_point) | 用一张主体偏边的照片分别看横幅与方图。若缩略图只剩一面墙，单独调整裁切；用长标题再查一遍遮挡。 |
| 白字只在设计师挑的暗图上好看 | W3C 的 G18 看字形紧邻的背景。先试移动文案到照片留白处，再试只压暗文字下方；仍不稳定时将标题放到纯色区。标题用可缩放的原生文字。[W3C 局部对比技术](https://www.w3.org/WAI/WCAG22/Techniques/general/G18) | 选深街景和亮橱窗各一张，以真实字号采样文字附近最不利的背景。普通大小正文可参考 4.5:1 的可读性目标。另看未加载图片时能否认出标题和入口。 |
| 同尺寸的图标，一个像主按钮、另一个像装饰线 | GitHub Primer 会为不同显示尺寸分别画图标，用轮廓占比和线条调节视觉重量。分类插画可以有品牌个性；距离、收藏、导航等小图标优先用适合实际字号的同套简形。为小图保留触控区。[Primer 图标设计源文件](https://github.com/primer/design/blob/main/content/foundations/icons/design-guidelines.mdx) | 在实际手机尺寸并排看四个图标，再盖住文字试辨认；检查实心和线框的分量、底部对齐和细笔画。盖住文字只是诊断方法，最终页面保留有用的文字标签。 |
| 拖地图看看旁边，结果已经变了几轮 | Algolia 同时提供随移动刷新和手动重搜。城市探索页若查询走网络，首选移动结束后提供「搜索此区域」，保留当前搜索词与筛选。少量已加载的本地点位可随视口更新。地图中心变化不等于用户位置变化。[Algolia 地图检索](https://www.algolia.com/doc/api-reference/widgets/geo-search/js) | 连拖两个区域，选第二个搜索，再模拟第一次响应晚到。列表、图钉与已选区域应一致；未给定位时仍能搜区域，且不能把距地图中心误称为距用户。 |
| 页面显示可约，提交时却无法确认 | Cal.com 的问题讨论记录了可见时段与提交结果不一致，原因可能包括日历同步；它另有真正的临时预留接口。收到明确的名额冲突时，保留服务、人数与备注，标出失效时段并提供最新可选时段。遇到请求超时先查询原预约结果；只在服务端真的预留且给出到期时间时显示倒计时。[实际反馈](https://github.com/calcom/cal.diy/issues/23391) · [临时预留接口](https://cal.com/docs/api-reference/v2/slots/reserve-a-slot) | 在隔离测试环境用两人抢最后一席，再分别测同步错误和提交回执丢失。只让确认成功的人看到凭证；原因未确定时说明「暂时无法确认」，避免误报「已被抢走」。 |

## 让审美判断落到小程序页面

设计方向不靠“高级”“有质感”这类空话。画稿时分别决定以下三件事，并把理由写进设计确认单。

| 要决定什么 | 小程序里的默认判断 | 什么时候改变 |
| --- | --- | --- |
| 布局变化 | 工具、报名、订单、表单和后台入口优先稳定单列、共同对齐和明确下一步。首页可以用一张主图或一组分类建立记忆点，但不能让首屏只剩品牌装饰。 | 用户本来就是浏览灵感、看故事或看活动内容时，可让首图、图片比例和分组更有变化。每一种变化都在小屏回到一列，不能靠横向挤压内容。 |
| 信息密度 | 日常小程序保持中等密度。用分组、留白和标题划开任务，把用户此刻会比较的字段放在同一屏。 | 用户需要连续比对大量状态时，例如订单、时段、核销，采用较高密度和统一行高。照片、说明和低频入口后置。高风险提交页则降低密度，给确认、错误与帮助留空间。 |
| 动效 | 默认只给触摸、加载、提交成功和状态变化反馈，尊重系统“减少动态效果”倾向。 | 动效确实解释位置变化、列表刷新或提交状态时才加入。动效不能遮住按钮、延迟关键操作，也不能成为新手知道功能存在的唯一提示。 |

这套取舍来自 taste-skill 把“布局变化、动效强度、视觉密度”分开判断的做法，已改写为微信原生页面规则。[原始项目](https://github.com/Leonxlnx/taste-skill)

**反例。** “附近发现”页为了显得丰富，给每家店套大卡片、渐变背景、自动轮播和四枚标签。用户要比距离与营业状态时，一屏只剩一条半结果。首选改法是保留一条有辨识度的精选入口，其余采用可连续扫读的列表，距离固定在右侧，营业与人均放标题下，只保留真正能改变选择的标签。

## 一次可复用的评审

设计图、原型和真机页面都按下面顺序评。设计图只可以通过前两步，后三步需要实际页面或相应证据。

1. **保留有效设计。** 指出具体位置和理由，例如“首屏就能看到可报名时段”。看图可评按钮的位置和间距，实际触控范围要在可操作页面验证。
2. **按用户受到的影响排序。** 只列有依据的问题。每项说清元素、谁在哪里受阻、首选改法、验证动作。优先解决挡住主任务的问题，再处理会造成误选和返工的细节。
3. **按角色走主任务。** 选与项目有关的人，例如首次报名者、网络不稳的购买者、负责处理订单的管理员。观察他在哪一步要猜、返回或会误触。并列操作多到妨碍选择时，再考虑合并或分出主次。
4. **保住情绪高点和风险点。** 有结果时让用户看到下一步和依据。有钱、隐私、取消、失败或等待时，用清晰状态、可恢复路径和确切文案消除猜测，避免只靠颜色或转圈动画。
5. **在微信里复核判断。** 用同一批数据回到受影响的原生页面，实际点击相邻控件、调起输入法、从详情返回；对照截图核实文字截断和意外偏移。分开记录画面观察、开发者工具结果和真机结果。

评审交付采用如下短格式，适合在用户确认设计前直接阅读：

```text
有效点：报名按钮始终在当前选择的下方；失败后保留备注。

优先改余位提示：如果满额标记很难扫到，用户可能进详情后才发现不能报名。
首选改法：在时段标题下显示“仅余 1 位”或“已满”，并让已满项保持可查看但不能提交。
验证：放一场仅余 1 位和一场已满的演示数据，让首次用户分别找到可报场次和满额原因。
```

这个评审结构吸收 Impeccable 的“先说明有效点、按影响排序、每条给出原因和改法”的思路。微信原生页没有网页检测器可直接判断布局，视觉判断与真机操作仍须分别记录。[原始项目](https://github.com/pbakaus/impeccable)

交稿前再自己作答：「我在第一个屏幕找到了哪条结果？它为什么合适？谁会在什么情况下选错？改哪里最划算？」用正常与异常两组数据、窄屏和放大字体核对标题截断、标签换行、距离与操作区互相挤占。若列表空间不足，先删低价值标签，再试次要信息换行。涉及返回、复制、收藏、提交的结论需实际操作。
