# 业务回归

## 从一句需求到第一条可用路径

访谈时，把含混的词换成两个结果不同的例子。比如“可以取消报名”会影响剩余名额。先查已有约定和实现；确实未定才问“满员后甲取消，乙能立即报，还是要等负责人确认？”给出首选和代价，由负责人决定。用双方认可的名称，把角色、起始状态、动作和可见结果写回已有需求记录，保留未定分支。

设计获确认后，优先贯通一条包含真实页面入口、业务判断、存储和结果回读的最短路径，再向外扩展。例如团队选了立即归还名额，就依次验甲取消、乙能报名、负责人名单只保留乙的有效名额。先为当前一段写一个能观察结果的测试，看它按预期失败，再实现、重跑和整理；已有行为先建立基线。每次只引入下一段需要的能力。修复时在同一入口回归。简单本地工具可只走一次“启动 → 切后台 → 回来显示剩余时间”。

交付复核分两问：用户确认的每个结果在哪个入口看得到？实现是否符合项目的权限、兼容和维护约定？把没跑到的分支留给对应环境。此方法借鉴 [Matt Pocock 的需求访谈与工程技能](https://github.com/mattpocock/skills)。

## 运行与留证

1. 需求阶段用用户能判断的句子记录角色、动作和结果，例如“同一学生快速点两次，负责人名单里仍只有一条”。确认后的范围直接作为测试依据。
2. 开发时让页面和测试调用同一份业务实现。优先沿用项目测试工具；新建的简单 JavaScript 项目可用 Node 的内置测试运行器。时钟、本地存储、云数据库连接和平台注入的身份可以在测试边界替换。明确替换的部分及其验证局限，避免给测试单独实现一份业务。
3. 按场景选择用例。倒计时覆盖启动、应用切到后台、到期后重新打开和重复恢复；报名覆盖两名不同学生、同一学生重复或并发报名、管理员查表、普通人和伪造管理员参数越权。修复缺陷时补能复现该缺陷的用例。
4. 每次用空的测试数据启动；测试失败返回非零退出码。记录命令、运行环境、结果以及与实际环境的差别。多人项目进一步在测试云环境验证服务端身份、并发唯一性、权限和跨设备数据。模拟数据通过后，项目报告仍应写明待体验版验证的操作。
5. 向接手者交付一条可重跑的命令和预期结果。无相关能力的项目在报告标为“不适用”；不要为了填写报告给本地工具增加账号、管理员或云环境。

至少把一个核心场景测到实际入口可观察的结果：例如倒计时过期后调用真实页面的恢复方法，断言界面剩余时间为 00:00；报名调用真实服务端处理函数，断言负责人名单恰好增加一行。纯计算函数的正确结果可能被下一层展示或权限逻辑改错。

把「填备注、退出再打开、失败后重试、重复报名」作为首个实操案例时，使用[随包报名样板](../assets/signup-demo/README.md)。先记录页面状态，操作后等待可观察的结果；同时记录测试身份和名单条数。
