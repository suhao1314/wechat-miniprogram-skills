# 已上线项目版本更新

## 适用条件

项目存在正式线上版本，或用户说“已经发布了，想增加/修改……”时，使用本流程。版本更新仍在设计、环境准备、开发、发布四阶段内循环，不增加新的一级阶段，也不重新办理没有变化的账号、主体或备案步骤。

## 版本变更硬门禁

编码前先按 [development-stage.md](development-stage.md) 完成已有项目最小源码盘点，读取当前线上版本、项目进度、决策、测试报告和发布清单，再把本次变化写入 `docs/miniapp/version-change.md`。涉及 UI 时同时按 [miniprogram-ui-adapter.md](miniprogram-ui-adapter.md) 建立现有样式基线；局部更新默认继承，整体改版才重新比较三套方案。至少确认：

1. 当前线上版本和目标版本。
2. 用户可见的新增、修改、删除内容，以及明确保持不变的范围。
3. 页面和交互、数据库集合、字段、云函数、存储、身份权限、隐私、类目、域名和费用影响。
4. 旧数据兼容、迁移、失败回退和文件清理方式。
5. 需要重测的设备、角色、授权、异常和核心流程。
6. 是否需要更新隐私指引、用户协议、服务类目、备案信息并重新审核。
7. 审核员从首页进入变更功能的路径、测试账号或游客模式是否仍可用。
8. 是否引入旧登录接口、前端 openid、第三方 SDK、用户内容或支付签名兼容风险。

把事实、待确认项和智能体建议分开。就具体变更单提一个确认问题，接受指向该单的自然语言确认。多项歧义只追问未确定的部分；变更范围与上线授权分开记录。

## 变更分类

| 类型 | 示例 | 必须重新执行 |
| --- | --- | --- |
| 文案或低风险视觉修正 | 不改变功能、字段、权限或用户数据 | 受影响页面视觉验收、体验版回归、上传审核发布 |
| 功能更新 | 新页面、新操作、新业务规则 | 影响范围设计、开发、完整回归、体验版、审核发布 |
| 数据或云资源更新 | 新集合、字段、索引、云函数、存储目录 | 云端资源预检、权限审查、兼容/迁移、日志和回退 |
| 身份或隐私更新 | 头像昵称、手机号、定位、文件、分享范围 | 拒绝路径、修改/删除、实际隐私接口、平台指引、真机授权、重新审核 |
| 类目或资质相关更新 | 业务性质、交易、内容或受限能力变化 | 重新核对主体、类目、资质、备案和审核要求 |
| 审核路径或账号更新 | 入口层级、登录方式、会员/付费可见性 | 审核员可达性、测试账号、退出账号、审核说明和完整流程 |

一个更新可能同时属于多类，取所有适用门禁的并集。

## 状态记录

- `project-plan.md` 保留当前产品和线上事实。
- `progress.md` 同时写“线上版本”和“开发中版本”，不得把开发中状态覆盖线上版本。
- `version-change.md` 保存本次目标版本、影响、确认和回退信息。
- `test-report.md` 标明测试对应的具体版本、环境和设备。
- `release-checklist.md` 每个目标版本单独完成上传、体验、审核和发布记录。
- `decisions.md` 记录数据、身份、隐私、费用或兼容性的重要选择。

发布完成后，把目标版本转为线上版本，记录发布时间和回退信息，再运行 `python scripts/validate_project_state.py <project-root>`。只有状态一致性检查没有错误时，才宣称本次版本闭环完成。
