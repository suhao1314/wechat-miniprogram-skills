# 微信小程序分阶段交付规范

适用于工具、报名、交易、内容等微信小程序。按本次业务选择相关条目。已确定的事项跨阶段沿用。

## 已确定的方向

面向第一次做微信小程序的人，只提供一个入口。用户可以从一句模糊想法开始，由 AI 追问会改变产品的事项，记住已经决定的内容，按阶段调用专门技能。需要本人操作时，每次讲清打开哪里、点什么、看到什么算成功。记录进度、失败原因和下一步，换一次对话也能接着做。

## 已确定的正式开发条件

1. AI 先和用户讨论清楚本次版本的目标、使用角色、业务规则、开发方向和实施方案。把技术选型、前后端分工、数据与权限、外部依赖、费用、性能目标、测试与交付方式准备齐全。用大白话说明每项关键选择对使用体验、成本和维护的影响，并记录用户决定。
2. 按角色列出本次范围内的全部页面，包括约定的管理端。逐页提供可看的 UI 设计图，标明入口、操作后的去向，以及适用的加载、空数据、失败、成功和权限状态。用页面清单逐项对照设计稿，让用户能沿主要任务从头看到尾。
3. 按页面列出全部图标及所需状态，备齐实际图标、配图和必要源稿，注明用途、来源、授权和导出规格。向用户一起展示页面设计和图标，记录选定版本。
4. 正式编码前，由用户确认上述方案、全量页面 UI 和素材均已齐备。缺项直接指出并补齐；后续需求变更只复核受影响的页面、素材和技术决定。

## 已确定的交付质量要求

### 用户编号与昵称

需求阶段用场景判断：客服或管理员要按号找人吗？同名用户需要互相确认、分享资料或发起交流吗？有长期账号时主动给出建议；纯本地工具可跳过，只有后台管理需求时编号可仅对本人和授权管理者可见。记录唯一范围、可见人群、查找与联系权限，纳入数据模型、个人页、管理后台和测试方案。

同一产品内每个账号有稳定的内部主键。对人展示的号码优先短、好记、易口述，按字符串保存。根据预计累计发号量、注销不复用、预留号和增长余量选长度。几百到几千人优先评估 5 位，预计上万也先算 5 位是否够用，再考虑 6 位。首位避开 0 时，5 位有 90,000 个候选号，6 位有 900,000 个；扣掉保留号后计算可用量。约定余量不足时启用更长新号，老号继续有效，查找和复制兼容两种长度。服务端分配，账号映射与展示号分别约束唯一；并发首次登录或请求重试取回已有编号，碰撞则重试。展示号不编码手机号、学校、身份或权限，改名换校不改号；已有账号先查旧编号和引用，缺号才补。跨客户项目独立编号，跨学校是否允许查找单独决定。

规划时问清昵称是否允许重名、能否修改，以及谁有权使用官方身份标识。提供允许重名与要求唯一两种方案，由项目用户决定；允许重名时以唯一用户号区分，官方账号的认证标识由后台授予。若业务要求昵称唯一，明确唯一范围与空格、大小写等比较规则，在注册与改名时由服务端统一校验，并发抢名只允许一个成功。

默认本人可查看和一键复制；授权管理员按完整号码精确查找并校验管理范围。用户互搜、跨校查号、按号发消息仅在项目方选择开启后启用，遵守可见范围、拉黑和联系设置；公开编号仅用于定位，所有敏感操作仍由服务端鉴权。验收覆盖同名找人、并发重试不重号、跨范围查询、猜号限频及注销后旧号不指向其他人。

### 昵称与用户发布内容的风险控制

开发前按实际开放的入口列清审核对象：注册和修改昵称、头像、简介、帖子标题、正文、配图、问答和评论。和运营方确认违规与冒充规则、谁处理举报、误判如何复核；选型时核对微信当日官方内容安全能力、适用范围和成本。

审核在服务端生效，覆盖新增和编辑。清楚区分通过、待审、拒绝；异步图片未返回或审核服务超时时，相关内容保持待审并可重试。待审内容不得经列表、详情、搜索、分享入口提前公开；已发布内容编辑期间默认展示上次通过的版本；管理员下架优先于版本展示，所有入口同步执行。给作者明确状态、修改或申请复核的入口。后台记录举报、处置理由和复核结果，限制审核员权限。

用测试账号验证本项目选定的重名策略、冒充官方、违规昵称、正常发帖后改为违规内容、图片待审、审核超时、举报下架和误判恢复；同时验证普通用户看不到待审版本。只对本项目实际提供的功能执行对应检查。

- 性能：设计阶段规划分包、分页、缩略图、按需加载和缓存。交付时在同一台手机、相近网络下记录冷启动到首屏内容可见的时间、连续滑动表现和返回列表的重复请求；优化后以相同条件复测。
- 文本：按字段选择交互。帖子正文支持长按选字复制，取件码、订单号、活动地址提供一键复制，报名备注、群公告输入框支持粘贴多行中文。用测试文本复制到微信对话输入框再粘贴回来，核对完整性、换行、首尾空格与操作反馈。
- 成本：先确认使用规模和预算。按“日活人数 × 人均浏览帖数 × 每帖平均实际下载图片字节数”估算每日图片流量，另估数据库读取次数及适用的存储、云函数费用。用当前计费口径比较原图与缩略图、缓存与重复读取的成本，约定用量提醒。
- 素材：程序自带的页面、导航、按钮、提示、空状态和示例文案默认均禁用 emoji，只有用户明确要求的场景才使用。此设计规则约束产品提供的界面和文案；用户投稿是否允许表情属于内容规则，另按业务需求决定。
- 允许使用授权适用的第三方图片和图标库。通用控件和图标优先从腾讯 TDesign MiniProgram 或项目已有的合适资源中选择；没有合适图标时自行绘制矢量图，统一线宽、尺寸和选中态，保留可编辑源稿。品牌插画和业务配图可自绘或生成；按展示尺寸压缩成小写 .png 或 .jpg，原生底部导航准备本地 .png。正式页面使用确定的素材。

## 各阶段调用入口

### 产品内新手引导

1. 在全量 UI 确认前，分别从首次使用小程序的用户和首次接手后台的管理员出发，列出容易找不到入口、需要跨步骤或误操作代价高的任务。逐项给出推荐理由、出现时机、角色和操作目标，请项目方选择采用、调整或跳过。简单且一眼能懂的操作可建议只保留清晰的按钮文字。把选择记入页面清单。
2. 微信小程序使用 TDesign MiniProgram 的 Guide（t-guide）。例如第一次报名时指出提交入口，成功后在结果页提示在哪里查看报名进度。表单、弹窗、选择器等优先查同版本腾讯组件库，结合项目已有组件、样式和分包体积按需引入。[TDesign Guide](https://tdesign.tencent.com/miniprogram/components/guide)
3. 网页后台使用 Driver.js，例如带新管理员找到待审队列、打开详情、理解处理结果。按角色过滤步骤，演示审核或删除时使用测试数据或仅说明操作。查项目实际安装版本并使用其支持的 API；目标元素渲染并可见后再展示，目标缺失时跳过或退出。[Driver.js 官方用法](https://driverjs.com/docs/basic-usage)
4. 每步只提示一个动作，提供跳过和重新查看入口。按项目、账号或本地使用者、角色、引导版本记住已完成或跳过状态。设计稿覆盖打开和关闭状态；用首次进入、跳过后重进、主动重看、权限不足、小屏定位和返回页面验证。分别保存引导展开与关闭时的截图基准，并实际点击验证浮层退出后原任务仍可继续。

| 环节 | 工作流应负责什么 | 验收依据 |
| --- | --- | --- |
| 需求与首版 | 用生活化问题确认角色、核心操作和首版目标，复用已有答案 | 新手能描述一个可验证结果。试题可用“学生报名后，负责人看到名单” |
| 原生 UI 与交互 | 在同一组业务数据下比较设计，覆盖胶囊避让、长文、多图、空状态、失败重试和重复点击 | 分清设计原型、微信开发者工具实机模拟和手机真机效果 |
| 素材 | 按已确认的图标与配图清单制作或引入资源，按用途放分包或云存储 | 核对图标来源、底部导航普通与选中态、实际资源和包体积，检查界面文案是否遵守 emoji 规则 |
| 原生开发与复用 | 按需调用小程序开发技能。帖子、问答等业务模块单独接入，使用当前客户的身份、权限和数据 | 在当前项目跑通用户任务；复用桂校园代码时核对项目专属依赖 |
| 云开发接入 | 用户选择腾讯云开发后读取 https://docs.cloudbase.net/skill.md 的最新微信小程序分支。盘点现有工具、站点、AppID 和环境；缺什么补什么。按实际登录方式指导扫码 | 环境 ID 与项目配置一致并通过只读检查；另行确认微信开发者工具已登录、能打开并预览项目 |
| 云后台与管理端 | 云后台按需处理数据库、索引、存储、云函数和权限。业务管理端按实际角色设计，例如负责人看名单、审核内容 | 用授权角色执行核心操作，验证普通用户无法访问。后台是否内嵌小程序或独立 Web，按项目决定 |
| 微信页面验收 | 优先复用同级 wechat-page-qa。按已有授权操作开发者工具，进入目标页面、点击、截图、查日志、修复后复测 | 记录路由、测试动作、可见结果；模拟器、安卓、iPhone、体验版和生产结果分别标明 |
| 性能与成本 | 评估冷启动、列表分页与滑动、图片规格、返回时重复请求、分包。结合预计访问量、读取次数和图片流量估成本，核对现行计费与提醒 | 提供设备、网络、测量结果与用量假设；性能目标和预算按项目确定 |
| 文本操作 | 正文按需要长按选字复制，取件码或地址可一键复制，输入框支持粘贴多行中文 | 实际复制和粘贴，检查截断、换行、空格与反馈 |
| 备案与交付 | 指导账号、备案、体验版、审核、发布及退回后的处理；核对当前官方要求，提示账号负责人操作及结果 | 留下体验与发布状态、版本、已测范围和待验证项 |

## 开发前确认主体、类目与资质

需求访谈一旦识别实际业务，在确定技术路线、购买资源和制作全量 UI 前，与用户核对以下事项。开发中新增公开发帖、互动问答、交易等能力时，重新核对受影响的类目与资质；提审前复查平台当天要求。

1. 确认谁实际运营、账号注册在谁名下、是否有管理员配合。区分个人、个体工商户、企业、学校或其他组织；社团名称不能推定为学校主体，受托开发者也不等于运营主体。
2. 按真实功能列出拟用类目。以校园社区为例，询问谁能发布、谁可见、是否评论或问答、是否收费；查微信当日开放类目、资质示例，再核对该账号后台可选项。把用户内容审核、举报和处置责任纳入业务方案。
3. 分别核对四件事：微信类目准入材料；小程序自身备案；自有网站或后台域名所涉注册、实名与 ICP 备案；实际接口的服务器域名或内嵌网页业务域名配置。即使选 CloudBase，也要核对业务类目单独要求的证明。逐项查已有材料、主体归属和适用条件，再判断是否需要新域名或申请。
4. 给用户一张可执行清单：功能、运营主体、可申请类目、所需证明、已有与缺失、办理入口、经办人、先后依赖、官方披露的时间费用、核验日期和下一步。区分已核实可推进、待补材料、当前主体不适用、需平台确认；待审核的材料单列。按当日情况推荐补办、核实实际运营主体或协商调整首版功能。只记录核验状态，证照由持有人在官方平台提交。
5. 官方入口：[微信开放类目表](https://developers.weixin.qq.com/minigame/product/material/)、[社区/论坛资质示例](https://developers.weixin.qq.com/minigame/product/material/shejiao/shequ)、[小程序备案办理入口（登录微信公众平台）](https://mp.weixin.qq.com/)、[腾讯云备案域名准备](https://cloud.tencent.com/document/product/243/18905)、[腾讯云开发接入](https://docs.cloudbase.net/skill.md)。遇到公开指引与后台不一致，记录差异，请账号管理员通过平台核实。
