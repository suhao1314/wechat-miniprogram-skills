## 目的

让 UI 方案从一开始就像微信小程序，并能转换为原生 WXML/WXSS/JS/JSON。HTML 只承担可点击预览和并排比较，不得用网页设计习惯决定页面结构，也不得把通用 Web UI Skill 作为默认设计来源。

## 来源优先级

按以下顺序获取设计依据：

1. 微信官方[小程序设计指南](https://developers.weixin.qq.com/miniprogram/design/)和平台组件规则。
2. 项目已有品牌资产、截图、设计 token 和组件。
3. 一个成熟的小程序组件体系：WeUI、TDesign MiniProgram、Vant Weapp 或原生组件。
4. 已安装的小程序或移动 App 设计 Skill。只借用需求提问、手机框比较和设计检查方法；不得直接继承其 Web 技术栈、现代 CSS 或平台假设。
5. 社区模板和案例。使用前检查当前版本、许可证、维护状态和页面是否适合本项目，不按 Star 数自动采用。

没有合适第三方 Skill 时，直接使用本文件完成设计，不回退到通用网页设计流程。

## 设计输入

首版范围确认后，只补问会改变 UI 的缺失信息。优先使用结构化提问工具，一轮最多 1-3 个问题：

- 用户更希望“像微信、容易上手”，还是“有自己的品牌感”；不确定时保留两种方向供比较。
- 是否已有 Logo、品牌色、参考截图或必须复用的界面。
- 主要在现场快速操作、日常反复查看，还是需要大量填写；这决定信息密度和主操作位置。

不要让用户用抽象设计术语描述风格。用户没有视觉偏好时，直接生成三套可见方案让他比较。

## 逐页判断入口的轻重

出 UI 图时，逐页说清用户来这里主要做什么、哪些入口需要随时找得到。按使用时机、操作后果和找不到的代价选择位置、分组与样式。遇到两个合理排法，向用户展示推荐排法并用一句日常语言解释原因。

例如在已登录的「我的」页，收藏、报名等常用操作靠前；长期备查的《用户协议》《隐私政策》可以在页尾各设一个文字链接。隐私请求、申诉等需要发起和跟踪的事项，要有名称清楚、容易找到的办理入口。登录时若涉及用户作出同意选择，把相应条款放到决定发生的位置。换成隐私中心时，根据该页的主要任务重新排序。

验收时用实际小屏页面检查文字对比度、换行、底栏遮挡和两个链接的点击范围，分别点开核对目标页。像素差异只能定位变化；首次设计以及改版都要按任务复核入口是否合适。

设计确认前，用用户最常做的一件事走一遍每页。每块内容必须帮助理解、决策或操作。合并重复入口，删除无用途的统计卡、口号和装饰块；空列表只保留必要说明和可行的下一步。小屏首屏优先给业务内容和主要动作，保留阅读间距与触控空间。检查键盘弹出、长文本和有数据时能否顺利操作。

逐页判断哪些信息需要带走、哪些输入丢失后重填费力。正文按需支持长按选字；订单号、地址等按用途一键复制原值并反馈，备注支持粘贴多行。长帖或复杂表单按场景提供草稿，明确保存时机、返回后恢复、主动丢弃和提交成功后清理；提交失败保留输入，账号切换隔离草稿，敏感字段单独决定是否可保存。简单选择或即时搜索通常可省草稿。把适用项写进页面状态与业务验收，用实际操作验证。

## 页面设计评审

直接回应「哪个好」「哪里不方便」，也在展示方案、原型和开发后的页面时主动评。先确定谁在什么情况下来做哪件事。有图就看图，有可操作的页面且在授权范围内就走一遍；只有需求或源码时给设计建议，指出需要看到哪个页面状态才能验证。

- **看第一眼，再走到结果。** 先指出页面上最抢眼的具体元素，再指出用户要找的内容或动作在哪里。沿着一次真实任务找多余的查找、记忆、切页、重复输入或出错后返工。判断视觉时看实际文字是否能扫读、相关信息是否靠在一起、留白和强调色把注意力引向哪里。保留有效的排法。
- **提出能直接动手的改法。** 按对主要任务的影响挑最值得改的几处，指到具体文案、控件或区域。用「这里现在怎样 → 谁会在哪一步费劲 → 我会怎么改 → 怎样验」说明。把品牌风格偏好与影响使用的缺陷分开。证据支持现状时可以保留，无需凑数。
- **替新手拿主意。** 有多个方案就明确首选，比较同一任务在各方案中要看什么、点哪里，以及首选牺牲了什么。用户提出两个用途时，分别给首选；只有能确定主要用途时才给默认方案。先用现有元素解决问题，提出新功能要有独立理由。三套只换颜色或圆角时，说明它们的操作路径相同。没有成图时可以判断信息如何安排，实际配色、排版和照片质量留到看图后评价。
- **用实页校正判断。** 对最重要的修改，用同屏宽、同数据、同状态复看并执行对应动作，比如找场次、纠正错误后重新提交。列出已看到的和仍待点击或真机验证的。点击次数、用时和误触率只报告实际记录；Pixelmatch 可定位变化，使用是否更方便要回到任务本身。

例如，第一次报名的人要选一场有余位的活动。若列表卡片把海报和标题放在首屏，场次与余位要进详情才看见，我会把日期、校区和余位放在每行标题下面，让学生在列表里直接比较；保留缩略图辨认活动。代价是每行多占一行文字。用「这周六、本校区、还有名额」在两个版本各找一次，观察是否还要反复进详情。若页面的主要任务是浏览摄影作品，大图的优先级就不同。

## 已有项目样式继承

继续已有项目时，先建立样式基线再修改 UI；新项目仍按下一节生成三套方案。基线至少来自：

1. `app.json` 的 `window`、`tabBar`、主题和页面配置。
2. `app.wxss`、公共 WXSS、主题文件和设计 token。
3. 目标页面 WXML/WXSS/JSON、公共组件和当前主组件库。
4. 项目内图标、图片比例、空/错/加载状态及现有真机截图。

在 `docs/miniapp/design-system.md` 记录以下可复用事实：

| 类别 | 记录内容 |
| --- | --- |
| 视觉 token | 主色、辅助色、字号层级、间距、圆角、边框和反馈状态 |
| 页面结构 | 导航、内容层级、列表/表单模式、底部操作和安全区 |
| 资源 | 主组件库、公共组件、图标来源、图片比例和裁切方式 |
| 数据映射 | API/存储字段如何显示、空值与异常值如何降级 |
| 差异 | 无法继承的部分、原因、影响页面和回归范围 |

新增页面默认继承现有项目的 token、组件和交互习惯。不要从外部案例照搬固定 `vw`、字号、4px 圆角或统一卡片结构；现有项目基线优先，同时仍满足微信胶囊、安全区、触控区域和 WXML/WXSS 可落地要求。用户明确要求整体改版时，才重新走三套方案比较和完整视觉回归。

## 三套方案合同

把三套方案保存到 `docs/miniapp/ui-options/index.html`，用同一关键页面、同一业务数据和同一功能范围公平比较：

按内置的[页面构思与打磨](mobile-design-directions.md)选出三种排法，直接用用户能理解的动作给方案命名。优先评估微信原生和 TDesign MiniProgram，选定一个主组件体系；三套共用该体系。每种方案展示哪个信息更靠前、哪个决定更容易做、代价是什么。已有项目沿用既有主组件库。

比较页面可以使用普通 HTML 排列手机框；手机屏幕内部必须遵守以下要求：

- 固定使用 375px 或 390px 宽的竖屏画布，并在整个项目保持一致。
- 显示状态栏、微信右上角胶囊、顶部避让区和底部安全区。
- 使用真实中文文案和接近真实的模拟数据，不使用 Lorem Ipsum、Hero、营销口号或设计流程说明。
- 三套方案必须展示真实产品首页或最高频任务页，不能只展示色板和组件样例。
- 显示底部导航时采用 2-5 项，优先不超过 4 项；每项有正常态和选中态。
- 每个可点击区域至少约 44px；交付到小程序时对应约 88rpx 的舒适点击区域。
- 方案名称、实现难度和差异说明放在手机框外，不污染真实界面。

先逐版看手机原尺寸画面，按主要任务给出首选。再让用户选择一个方向、组合明确元素或继续修改；用户选定后生成完整高保真原型。

## 小程序硬约束

| 设计问题 | 必须采用的处理 |
| --- | --- |
| 微信胶囊 | 预览中固定显示并留出空间；开发时用 `wx.getMenuButtonBoundingClientRect()` 动态计算，不硬编码真机位置 |
| 顶部导航 | 标题、返回和页面操作避开胶囊；自定义导航必须说明返回路径和系统状态栏适配 |
| 触控区域 | 关键按钮、图标按钮和列表操作至少约 88rpx；视觉图标可以更小，点击区域不能缩小 |
| 底部安全区 | 固定按钮、自定义底栏使用 `env(safe-area-inset-bottom)`，并在 iPhone 和安卓真机检查 |
| 原生 `tabBar` | 图标使用项目内本地 PNG，同时准备 `iconPath` 和 `selectedIconPath`；不使用网络图片、SVG、iconfont 或 emoji |
| 自定义 `tabBar` | 仅在原生样式确实无法满足已确认方案时使用；必须处理选中态、页面同步、安全区和所有入口回归测试 |
| 字体 | 默认使用微信运行环境的系统字体；不依赖 Google Fonts、远程字体或未授权字体 |
| 图片和图标 | 优先使用主组件库图标或有许可证的项目内资源；关键文字不能做成图片 |
| 状态 | 数据页面至少设计正常、加载、空、错误；涉及权限时再增加拒绝授权和重新操作路径 |
| 适配 | 检查窄屏、长文字、字体放大和键盘弹出，不照搬桌面多栏或固定宽度网页布局 |

## WXML/WXSS 可落地门禁

用户选定方向后，生成完整原型前先检查每个核心视觉和交互。把结果写入 `docs/miniapp/design-system.md`：

| 原型元素 | 小程序实现 | 组件来源 | 风险或降级 |
| --- | --- | --- | --- |
| 主按钮 | `<button>` 或对应组件 | 当前主组件库 | 加载、禁用、按下态 |
| 页面卡片 | `<view>` + WXSS | 原生或当前主组件库 | 阴影和圆角在安卓真机检查 |
| 底部导航 | 原生或自定义 `tabBar` | `app.json` 或组件 | 本地 PNG、选中态、安全区 |
| 顶部导航 | 原生导航或自定义导航 | 微信平台能力 | 胶囊动态避让 |

每个承载品牌识别或主要操作的效果都必须有明确的小程序实现。找不到可靠实现时，按顺序处理：

1. 改成 WXSS 可实现的等价效果。
2. 适合静态装饰时，预渲染为已授权并压缩的小写 png 或 jpg，记录体积与适配方式。
3. 仍不可行时，从候选和原型中移除，不能只在交接文档写“开发时再想办法”。

禁止把以下内容作为核心视觉或主要交互：

- Landing Page、Hero、桌面导航、转化漏斗、社交证明等网页结构。
- Three.js、WebGL、GSAP、视差、鼠标 hover、键盘专属交互。
- `backdrop-filter`、复杂 `clip-path`、`:has()`、容器查询或滚动驱动动画。
- 远程 CDN 图标、远程字体、外链脚本、需要浏览器扩展或 Web 运行时的能力。
- 只能在 HTML 中成立、没有 WXML/WXSS 映射的装饰和组件。

非核心装饰若使用现代 CSS 方便预览，也必须提供已验证的降级效果；关闭该效果后，信息层级和品牌识别仍应成立。

## 主动查找交互技巧

设计新流程时，从用户最容易中断、重复操作或误触的步骤选题。先查已有规则，再主动查微信设计指南、TDesign 小程序示例或相关原始设计指南。对适用的技巧记录来源、适用条件及一个可执行的验收动作。将网页案例转成手机触控场景，核对目标端能力。已有方案能解决问题时直接复用。

- 多图排序可以长按拖动。若主要目的是选封面，在图片菜单提供“设为封面”，验收时仅用点按把最后一张设为封面。[W3C 拖动操作](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
- 固定底栏可能遮住列表末项。网页后台用键盘逐项移动焦点检查遮挡，小程序用短屏实际滚到最后，确认末项可见可点。[W3C 焦点遮挡](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- 多人报名中，若联系人也是一名参加者，提供“使用联系人资料”并允许修改。换成他人报名时核对资料归属，已失效的信息重新填写。[W3C 重复输入](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html)

## 组件选择

确定字段前先问这个值有什么用途、能否省去或沿用已知值。根据选项数量与长度、用户是否知道答案、输入精度、设备和改错成本选择控件。把选择理由和易错状态放进可点击原型。遇到新场景，同样走一遍首次使用、熟练使用和出错后恢复。

- 输入前后都能看到字段名。固定标签或浮动标签均可。提前说明容易填错的单位或要求。统一标记必填或选填，避免只用颜色传意。失焦或提交时就近提示具体改法，修正后清除提示，提交时定位首个错误。
- 确需验证码时支持整串粘贴、退格修正和过期重发，分格可共用一个输入框。系统自动填充需在目标设备验证。密码按需支持显隐，创建时提示实际规则，密码与验证码排除在草稿外。
- 少量短选项直接展示，需要浏览时用选择器，大量已知名称支持搜索匹配。展示无匹配状态，忽略过期查询结果。有上下级关系时联动筛选，切换上级后清掉失效值。
- 单日与连续日期范围分别设计，跨年选择提供快速选年。粗略范围可用滑块，精确值可直接键入，组合使用时同步数值和单位。
- 手机上传提供点选入口，桌面后台可加拖放。选择前说明限制，每个文件可辨认上传状态，失败项可单独重试或移除。
- 延伸到其他页面时，列表返回保留筛选和位置，耗时操作显示当前状态并防重复提交，可撤销的操作给恢复入口。按实际任务取舍。验收时用真实操作检查，例如快速更换两次学校、粘贴以零开头的验证码、只重传一张失败图片。

- **WeUI / 原生组件**：适合快速上线、微信原生感、轻量表单和设置流程。
- **TDesign MiniProgram**：默认优先评估，适合表单、列表、数据、工具和业务流程，并允许品牌 token 定制。
- **Vant Weapp**：适合已有 Vant 项目或组件模式高度匹配的移动业务；不要只因为组件数量多就采用。
- **自研组件**：只在现有组件库无法满足关键品牌或交互时增加，不能重造基础按钮、表单和反馈组件。

一个项目只选一个主组件库。设计阶段只记录选型和来源；除非用户已经授权进入开发，不安装依赖、不复制模板源码。

## 原型与交付

选定方向后，完整原型覆盖约定范围内的页面和适用状态；单页工具直接验证同一页的状态变化，证明用户能完成首版核心任务。原型使用手机画布、真实文案和可点击跳转，并覆盖导航、主要表单、加载、空、错误和拒绝授权状态。

`docs/miniapp/design-system.md` 至少记录：

- 375px 或 390px 画布基准和胶囊避让方式。
- 方案来源、参考链接、版本快照、许可证和采用/舍弃原因。
- 颜色、字号、间距、圆角、按下态和状态反馈 token。
- 主组件库及每个关键组件的 WXML/WXSS 映射。
- 原生或自定义 `tabBar`、本地图标清单和安全区方案。
- HTML 专用效果、对应降级方式和仍未完成的真机验证。

始终告诉用户：HTML 原型用于确认视觉和流程，不是最终小程序；最终效果以微信开发者工具和安卓、iPhone 真机为准。

用户希望看具体取舍时，打开[三组可操作的微信原生正反例](native-field-guide.md)，报告实际操作和结果。
